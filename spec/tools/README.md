# spec/tools: the reference release tool

`release-tool.mjs` is runtime's own verifier, bundled into one file, for the release path of every
AirplaneMode-Labs package (spec release 0.6.1, manifest 0.1.4, [MANIFEST.md](../MANIFEST.md) "Release manifests").
It is generated by `npm run spec:release-tool` from `src/release/` (tsup, platform node, ESM, target node22,
nothing minified) and committed here with `release-tool.mjs.sha256`. It is **not** in the npm package. Other repos
vendor it byte for byte (`scripts/release/release-tool.mjs` with `VENDORED.json`); control-plane's `cp-sign` is
the production signer and is checked against this tool on `vectors/release/`.

It is a rehearsal tool and a verifier. It can sign with exactly one key, the published RFC 8032 TEST 1 key, and
only for `-rehearsal` ids. It cannot sign a release: a real release is signed offline by the owner with
`cp-sign sign --no-expiry`. It reads no key file and has no option to name one.

```sh
node release-tool.mjs manifest --dir D --id ID --version V --licence SPDX --publisher release|rehearsal
node release-tool.mjs sums     --dir D
node release-tool.mjs sign     --dir D --test-key rfc8032-1
node release-tool.mjs verify   --dir D --expect-id ID (--trust-file docs/release-keys.json | --trust-test-key) [--allow-test-key] [--now T]
```

`D` is a flat release directory that holds only the artefacts, `release-manifest.json` and `SHA256SUMS`.
`manifest` lists every regular file except the manifest and SHA256SUMS (the file name must be lowercase and match
`[a-z0-9][a-z0-9._-]{0,127}`); `createdAt` is `SOURCE_DATE_EPOCH` (a decimal integer) when set, so two runs with the
same value write the same bytes. `sums` re-hashes each entry and writes `SHA256SUMS` (LF, sorted, artefacts only).

## The rules the tool enforces

- R1: it never signs an id that is not `<package>-rehearsal` with the test key: `usage: test_key_release_id` (exit 2).
- R2: `verify` needs `--expect-id`; the test-key flags need a rehearsal id and never go with `--trust-file`.
- R3: `--allow-test-key` and `--trust-test-key` exist only on the command line. The one environment variable the
  bundle reads is `SOURCE_DATE_EPOCH`; a test counts the reads in the bundle.
- R5: no `expiresAt`.
- Every directory and member is checked with lstat, then the file is opened and its identity re-checked with fstat:
  a symbolic link, a junction, a directory, a FIFO or any other non-regular member is `not_regular_file`, and a
  symlinked `--dir` is refused by all four commands.

## Exit codes and output

| Exit | Meaning | Output |
| --- | --- | --- |
| 0 | accepted | stdout `{"verdict":"ok","id","version","entries","testKey"}`; stderr `VERIFIED WITH THE PUBLISHED RFC 8032 TEST KEY: rehearsal only, not a release` when `testKey` is true (taken from the signature that verified, never from a flag) |
| 1 | an I/O error (a missing directory, a read error, a crash) | stderr `error: ...`; never a refusal |
| 2 | a usage error | stderr `usage: <token>: <message>`; stdout empty |
| 3 | refused | stderr `refused: <reason>` first; stdout `{"verdict":"refused","reason":"<reason>"}` |

The reasons and tokens are `RELEASE_REJECT_REASONS` and `RELEASE_USAGE_REASONS` in `../release.ts`, plus the
manifest reasons of `verifyManifest` (`test_key_refused`, `weak_key_refused`, `no_valid_signature`,
`unexpected_id`, ...). `usage: bad_arguments` is a command-line syntax error.

## Allowlist (tested by `test/release-tool.test.ts`)

The bundle imports only `node:crypto`, `node:fs`, `node:fs/promises`, `node:path`, `node:process` and `node:url`;
it holds no `node:http`, `node:https`, `node:net`, `node:tls`, `node:dns`, `node:dgram`, `node:child_process`,
`node:worker_threads`, `node:vm` or `node:module`, no `fetch(`, `WebSocket`, `eval(`, `new Function`, `require(` or
dynamic `import(`; exactly one `process.env` read; and every 64-hex string in it is one of the five RFC 8032 public
keys, their keyIds or the TEST 1 seed. A rebuild must give the same bytes as the committed file.

## Vendoring

A consumer copies `release-tool.mjs` and `release-tool.mjs.sha256` byte for byte (they are `-text` in
`.gitattributes`, so a CRLF checkout cannot change the hash), records the digest and the spec release in
`scripts/release/VENDORED.json`, and runs every case of `vectors/release/release.json` through its copy.
