# Shared canonicalisation vectors

Generated by `node test/tools/make-vectors.mjs` (`--check` verifies); vendored byte for byte into
`control-plane/crates/cp-manifest/tests/fixtures/vectors/`. Both implementations (TypeScript
`canonicalize()` and Rust `canonical_bytes()`) must produce the `.canonical.txt` bytes exactly and,
under the RFC 8032 test seed (see `../examples/TEST-KEY.md`), the `.sig.txt` signature exactly.

| Vector              | Exercises                                                                       |
| ------------------- | ------------------------------------------------------------------------------- |
| 01-unsigned-example | the published unsigned example                                                  |
| 02-escapes          | quotes, backslash, every U+0000..U+001F, `/` and `<>&` in string values         |
| 03-devanagari       | non-ASCII Devanagari in publisher and licence (emitted raw, never `\u` escaped) |
| 04-minprofile-full  | nested MinProfile with all five fields                                          |
| 05-four-entries     | ids `m-x`, `m.x`, `m_x`, `mx` sorted by byte order                              |

`<n>.canonical.txt` holds the signed bytes: the prefix `airplanemode-manifest-v1\n` followed by the
canonical body (the manifest with `signatures` removed), with no trailing newline.

Negative vectors (`neg-*.json`) must be rejected by both implementations with the reason and at
the stage named in `negative.json` (`stage` is `parse` or `verify`):

| File                      | Reason               | Stage  |
| ------------------------- | -------------------- | ------ |
| neg-digit-key.json        | `digit_key`          | parse  |
| neg-float.json            | `float`              | parse  |
| neg-bigint.json           | `bigint` (2^53)      | parse  |
| neg-lone-surrogate.json   | `lone_surrogate`     | parse  |
| neg-unsorted-entries.json | `unsorted_entries`   | parse  |
| neg-dup-entries.json      | `duplicate_entries`  | parse  |
| neg-bad-url-http.json     | `bad_url`            | parse  |
| neg-bad-url-data.json     | `bad_url`            | parse  |
| neg-bad-url-blob.json     | `bad_url`            | parse  |
| neg-bad-spec.json         | `bad_spec`           | parse  |
| neg-bad-date.json         | `schema`             | parse  |
| neg-unknown-alg-only.json | `no_valid_signature` | verify |

Parse-level reasons (`digit_key`, `float`, `bigint`, `lone_surrogate`) take precedence over schema
reasons, which take precedence over the ordering checks. `neg-bad-date` carries
`createdAt: 2026-99-99T00:00:00Z`, which matches the RFC 3339 pattern but is not calendar-valid.
`neg-unknown-alg-only` is **schema-valid** (`alg` is any `^[a-z0-9][a-z0-9-]{0,31}$` token): it
parses, and its single signature is a correct Ed25519 signature under the RFC 8032 seed labelled
`future-pq`; a verifier must ignore it (never verify it as ed25519) and reject the manifest at verify
stage with `no_valid_signature` when the trust set holds the RFC 8032 key (`allowTestKeys`).
