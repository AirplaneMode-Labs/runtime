# Asset tamper vectors (runtime-specific)

Generated by `node test/tools/make-tamper-vectors.mjs` (`--check` verifies). Spec release 0.4.0. These
vectors check what an implementation that FETCHES assets does with bytes that do not match the signed
hash. They are runtime-specific: the `normative` fields of `expect.json` apply to any implementation that
fetches assets; the `informative` fields record only what `@airplanemode/runtime` returns, and another
implementation may return a different code and still conform.

| File                    | Content                                                                           |
| ----------------------- | --------------------------------------------------------------------------------- |
| asset-ok.bin            | 4096 bytes: byte `i` is `(i * 31 + 7) mod 256`                                    |
| asset-flip.bin          | the same with byte 2048 XOR 0x01                                                  |
| asset-truncated.bin     | the first 4095 bytes                                                              |
| manifest-ok.json        | one entry `asset-ok`, size 4096, the sha256 of `asset-ok.bin`, url `asset-ok.bin` |
| manifest-flip.json      | the same entry, url `asset-flip.bin`                                              |
| manifest-truncated.json | the same entry, url `asset-truncated.bin`                                         |
| expect.json             | per manifest: `normative` and `informative` expectations                          |

The three manifests are signed with `rfc8032-1` (a test key: the verifier needs `allowTestKeys` true) and
carry no `expiresAt`, so they do not expire. The URL is relative; it resolves against the manifest URL.

Normative for `manifest-flip` and `manifest-truncated`: `refused: true`, `bytesToConsumer: 0`, `getBlob:
'rejects'`, `blobUrl: false` (no `blob:` URL is created). `manifest-ok` is accepted and its 4096 bytes
reach the consumer. Each case runs on a FRESH memory store, never a shared or persistent one: a
persistent store would keep the asset or the downgrade state between cases.

Informative: `runtimeCode` and `runtimeReason` are the `AssetError` `code` and `reason` this runtime
returns from `ensure()` for the case (`null` when it returns none).
